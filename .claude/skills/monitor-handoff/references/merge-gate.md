# Merge-gate proof standards (read for every `agent:in-review`)

Run these checks before surfacing any merge-gate item to the human. The reviewer opens the PR later with **no session context** — the PR must stand alone.

1. **Direct-poll the PR's real state first** — `gh pr view <n> --json state,mergedAt,mergedBy,baseRefName`. The label monitor *and* issue search lag PR-merges by hours: `agent:in-review` can mean *already merged*. Never relay "awaiting merge" off the label feed.
2. **Proof must be IN the PR, before→after, for a cold reviewer.** UI change → before/after screenshots embedded in the PR body (chat images / worker-only previews are gone at review time). Backend/behaviour change → the e2e run with the scenario + the improvement over the prior state named (a bare "N passed" shows nothing changed). Don't accept "I verified" or a side-channel artifact.
3. **Match the proof's scope to the change's blast radius.** A wide change (a gate/validator/matcher touching a whole class) proven on the one or two *reported* cases hides costs the narrow proof can't see. If scope < blast radius, relay **"proven for `<cases>`; broader `<span>` unverified — sweep or merge eyes-open"**, never "ready, no caveats."
4. **Mock-built consumer of a cross-repo contract:** not merge-ready on its own mock tests as a *release*. Verify the real producer's contract against the consumer's assumption + require E2E proof against the live producer; producer not live+verified → surface as **"built, release-gated on `<producer>` E2E"** (`OPERATOR_MODEL.md` §Lifecycle 4). Default gate step, not human-prompted.
5. **A worker's own status summary is a lead, not fact.** Its prose ("still open", "merged", "done") is secondary and stale the moment written — direct-poll the primary source before relaying any status.
6. **Verify each pipeline hop independently — deploy ≠ data ≠ render.** A correct value at one hop doesn't mean the next reflects it, and a downstream gap isn't an upstream failure. Confirm the *render* hop on the live surface for "is it live?"; walk the hops for "why not showing?"; name verified-vs-inferred. For a **visual/quality** claim, look at the actual artifact (download + view) — metadata is not quality. **A public-surface UI change gets the cold-visitor read AT the gate**, on the PR's screenshots/preview (what does a stranger conclude in 5 seconds?) — pre-merge is the cheapest fix window. **For a data change/migration, enumerate the changed field's CONSUMERS** (every surface/derivation reading it) and verify each — checking only the display the change targeted is a proof-scope miss.
7. **A consumer-side patch that resolves display data from siblings / host catalogs / hardcoded maps is a CONTRACT GAP, not a fix to ratify.** If the payload doesn't carry what the consumer displays, the payload is incomplete — route the fix to the producer's contract (each block/response renders standalone) and gate the consumer on it. Ratifying the workaround ships the gap.
8. **Merged base matters:** flag prod vs staging base branches — a staging merge is not live; the outcome stays "pending live verification" until the deploy train ships and the live surface is checked.

## Stale in-review — the operator fallback close-out
For every `agent:in-review` issue whose PR is **merged**: if the merge happened well before the worker's close-out (label still on, issue open, no shipped-summary) and no worker session is active in that repo — **do the fallback yourself**: strip `agent:in-review`, close the issue if open, post one line ("operator fallback close-out — worker inactive; shipped: `<PR link>`"), reflect **Done** on the status view. Worktrees stay the worker's (its next sweep is idempotent). Ownership rule: `OPERATOR_MODEL.md` §Lifecycle 6.
